# ТЗ: «Второй мозг» — дневник-консультант на базе second_brain

> Техническое задание к [issue #1](https://github.com/dansury/second_brain/issues/1).
> Приложение к этому ТЗ: [`CJM.html`](./CJM.html) — путь пользователя (Customer
> Journey Map), читается с телефона, раскрывается по мере прочтения.
> Промты каждого слоя анализа — в папке [`Promts/`](./Promts/), по одному
> md-файлу на слой (см. §7).

## 0. О выборе инструмента для ТЗ

В issue #1 предложено установить скилл [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)
и писать ТЗ им. В репозитории уже установлен **GitHub Spec Kit** (`.specify/`,
коммит `815554a chore: install GitHub Spec Kit`) — это принятое ранее решение
использовать spec-driven процесс Spec Kit (`/speckit.specify`, `/speckit.plan`,
`/speckit.tasks`, `/speckit.implement` и т.д.) вместо BMAD-METHOD. Оба
инструмента решают одну задачу (структурированное ТЗ → план → задачи), но
Spec Kit уже интегрирован в этот репозиторий и в Claude Code, поэтому этот
документ — самостоятельное ТЗ на русском языке, а формализация в
`spec.md`/`plan.md`/`tasks.md` через Spec Kit выполняется на его основе отдельным
шагом (см. §9 «Дальше»). Устанавливать BMAD-METHOD параллельно не будем, чтобы
не вести два конкурирующих spec-процесса в одном репозитории.

## 1. Назначение

Бот — это не просто чат-ассистент, а **накопитель данных о пользователе**
(дневник + база фактов), который со временем становится **консультантом**:
анализирует новые решения и сомнения пользователя на фоне уже накопленной
истории (люди, повторяющиеся паттерны, прошлые решения и их исходы) и выдаёт
**прогноз** — насколько решение похоже на удачное или неудачное, и почему.

Ключевая идея: **чем больше бот знает** (дневниковые записи, документы, фото,
голос, рукописный текст, реакции пользователя на свои же прошлые советы), **тем
точнее прогноз**. Поэтому большая часть ТЗ — про то, как аккуратно и с
подтверждением пользователя превращать разнородный входящий поток в
структурированную Obsidian-базу, пригодную для многослойного LLM-анализа.

## 2. Каналы ввода данных

Бот получает данные тремя способами, все — через Telegram (существующий
транспорт hermes-agent):

1. **Дневник-канал или «избранное» (Saved Messages со вторым участником)**.
   Пользователь добавляет бота администратором канала-дневника, либо в чат
   «с самим собой» (либо в отдельный приватный чат, куда пишет только для
   бота). Бот **пассивно слушает** новые сообщения в этом источнике.
2. **Прямые сообщения боту** — пользователь сам пишет боту, что происходит,
   и какие есть сомнения. Это активный, разговорный канал: бот может задавать
   уточняющие вопросы.
3. **Вложения** — документ, фото (с людьми и/или рукописным текстом), голосовое
   или видеосообщение — присылаются любым из двух каналов выше.

Оба канала (1 и 2) проходят через один и тот же входной слой L0 (см. §6);
разница только в том, что в канале-дневнике бот не обязан отвечать на каждое
сообщение репликой — только фиксировать, лintить и (опционально) сигнализировать
о найденных решениях/сомнениях.

### 2.1 Автоматическое распознавание голоса/видео

Если новое сообщение в канале/чате — голосовое, оно распознаётся уже
работающим STT-пайплайном (Yandex SpeechKit, `speechkit/yc_stt.sh`, см.
README). Видеосообщения (Telegram video note / video) — новый функционал:
из видео извлекается звуковая дорожка → тот же STT; ключевые кадры (например,
1 кадр/5с или сцена-детектор) прогоняются через L-vision слой (§6.5) на предмет
лиц/действий, если это уместно (см. §5). Текст расшифровки и, если применимо,
краткое визуальное описание добавляются в дневниковую запись Obsidian **как есть**,
затем — как и текстовые сообщения — проходят L1–L3 и линт (§6, §8).

### 2.2 Документы

Присланный документ (PDF, DOCX, XLSX, изображение документа и т.д.) не
записывается в базу вслепую. Бот:

1. Определяет тип файла и извлекает текст (если это скан/фото — OCR).
2. Прогоняет черновую классификацию через промт `Promts/07_document_clarifying_questions.md`
   и **задаёт пользователю уточняющие вопросы**: что это за документ (договор,
   мед. заключение, скриншот переписки, счёт и т.п.), к какому периоду/человеку
   относится, публичный он или приватный.
3. Только после ответа создаёт заметку в Obsidian (`10_Documents/`) со
   ссылкой на оригинал (файл кладётся в `_attachments/`), с полученными
   метаданными во frontmatter, и лintит её (§8).

## 3. Персоны (действующие лица)

Ядро связности базы — люди, о которых пишет пользователь.

- Слой L2 (NER, `Promts/01_ner_person_extraction.md`) вычленяет из текста
  упоминания людей (имена, роли — «мама», «начальник Иван», «партнёр»).
- Перед тем как что-либо залинтить, бот **обязательно** прогоняет каждое новое
  упоминание через дизамбигуацию (`Promts/02_person_disambiguation.md`):
  ищет в базе кандидатов по имени/роли/контексту через gbrain (семантический
  поиск) и явно спрашивает пользователя в Telegram: *«Иван из этой записи — тот
  же Иван (начальник), что и в `Иван_Петров_(начальник).md`, или другой
  человек?»* с кнопками (существующий персонаж / новый персонаж / не уверен).
- Только после подтверждения текст линтится с проставлением `[[Имя_Фамилия_(роль)]]`.
- На каждого подтверждённого персонажа существует ровно один файл
  `20_People/Имя_Фамилия_(роль).md` (роль — в скобках, чтобы различать
  тёзок/разные роли одного имени: `Иван_Петров_(начальник).md` vs
  `Иван_Петров_(сосед).md`). Файл содержит frontmatter (см. §8.2) и растущий
  список ссылок на дневниковые записи, где он упомянут (Obsidian сам строит
  backlinks по `[[...]]`, но явный список тоже нужен для экспорта/грепа вне Obsidian).
- Если персонаж новый — бот создаёт файл-заготовку и спрашивает 1–2
  уточняющих вопроса (роль, как давно знакомы) для frontmatter.

Это даёт то, что просил пользователь: **на любой выгрузке базы видно, с каким
файлом-человеком связан каждый файл-запись**, и наоборот — карточка персонажа
показывает все связанные с ним записи.

## 4. Фото

### 4.1 Фото с людьми

Промт `Promts/08_photo_people_analysis.md`. Пайплайн:

1. Vision-слой определяет число лиц/людей на фото.
2. Бот спрашивает пользователя, **кто есть кто** (с привязкой к существующим
   персонажам через тот же механизм дизамбигуации §3 — можно ответить одним
   сообщением «слева направо: Иван, Мария»).
3. LLM-анализ (после того как роли расставлены) описывает: позы, взаимное
   расположение людей, вероятный контекст/что происходит, выражения лиц.
4. Ответ отправляется с кнопками 👍👎 (см. §5) и предложением редактуры
   («поправить, если не так»).
5. Итоговый разбор (после правок, если были) записывается и в дневниковую
   заметку (`10_Photos/`, со ссылкой на файл и на персонажей `[[...]]`), и в
   `Promts/_wiki/feedback.md` — как обучающий пример (§5).

### 4.2 Фото с рукописным текстом

Промт `Promts/09_handwriting_transcription.md`. Пайплайн:

1. Бот спрашивает, **чей это почерк**: мой / другого человека → чей именно
   (снова через дизамбигуацию персонажей, §3).
2. Распознаёт текст (OCR/vision-LLM), предлагает расшифровку.
3. 👍👎 + возможность правки текста пользователем.
4. Финальная (подтверждённая) версия сохраняется в `10_Photos/`, а
   **особенности начертания букв конкретного человека** — в
   `20_People/Имя_Фамилия_(роль).md#почерк` (частотные особенности: наклон,
   характерные буквы, сокращения), чтобы будущие расшифровки этого же человека
   учитывали накопленный профиль почерка (промт получает этот раздел как
   дополнительный контекст).

## 5. Обратная связь (👍👎) и маршрутизация модели по стоимости

**Любой** ответ бота (текстовый совет, разбор фото, расшифровка почерка,
уточнение по документу) сопровождается инлайн-кнопками 👍 и 👎.

- 👍 — фиксируется как положительный сигнал (счётчик в
  `Promts/_wiki/feedback.md`, без дополнительных вопросов).
- 👎 — бот спрашивает **что не так** (свободный текст), затем:
  1. Записывает в `Promts/_wiki/feedback.md` (append-only лог): дата, слой,
     использованная модель (провайдер+id), исходный ответ, что не так по
     словам пользователя.
  2. Предлагает **сменить модель** — список моделей текущего провайдера,
     отсортированный **по возрастанию цены за токен** (для OpenRouter —
     `GET /api/v1/models`, поле `pricing.prompt`/`pricing.completion`; для
     Yandex — статический прайс из конфигурации, см. `secondbrain/pricing.json`).
     Пользователь выбирает — вызывается штатный `/model <id>`.

Это создаёт петлю обучения: `Promts/_wiki/feedback.md` — материал для
периодического ревью промтов (человеком или отдельным слоем L6, см. §6.6) и
для итоговой статистики «какая модель на каком слое даёт больше 👎».

## 6. Многослойная архитектура анализа

Все текстовые/визуальные материалы, прежде чем стать «фактом» в базе или
основанием для прогноза, проходят через последовательность слоёв. Каждый слой
— это отдельный промт (файл в `Promts/`) и, где уместно, отдельный вызов LLM
(возможно другой моделью — дешёвые слои классификации не обязаны использовать
ту же модель, что и финальный совет). Слои спроектированы так, чтобы работать
и на «сырых» дневниковых записях, и на активном диалоге с ботом.

| Слой | Задача | Промт |
|---|---|---|
| **L0** — Приём и маршрутизация | Определить тип сообщения (текст/голос/видео/фото/документ/канал-дневник vs прямой чат), запустить нужный под-пайплайн (STT, OCR, vision) | `00_ingest_route.md` |
| **L1** — Нормализация и черновая классификация | Привести к тексту, определить: это фактологическая запись, решение, сомнение, вопрос, эмоция, или мусор/small-talk | `00_ingest_route.md` (общий с L0) |
| **L2** — Извлечение персон (NER) | Найти упоминания людей и ролей | `01_ner_person_extraction.md` |
| **L2.5** — Дизамбигуация персон | Сверить найденных людей с базой, спросить пользователя при неоднозначности | `02_person_disambiguation.md` |
| **L3** — Извлечение решений/сомнений/фактов | Вытащить структурированные «решение», «сомнение», «факт», «дедлайн», «участники», «ставка» (что теряется/приобретается) | `03_decision_doubt_extraction.md` |
| **L4** — Многоракурсный прогноз | Несколько независимых «взглядов» на решение: (a) исторические параллели из базы («в прошлый раз похожее решение с этим человеком привело к...»), (b) риск-ориентированный взгляд, (c) ценностный взгляд (соответствие целям/ценностям пользователя, если они зафиксированы в базе), (d) взгляд «адвоката дьявола» | `04_multiperspective_forecast.md` |
| **L5** — Синтез и оценка неопределённости | Свести взгляды L4 в один ответ: вероятностная оценка «удачно/неудачно» **с явной неопределённостью** (не ложная точность), обоснование, ссылки на конкретные заметки-первоисточники `[[...]]` | `05_advisor_synthesis.md` |
| **L6** — Обратная связь и ревью промтов | Обработка 👎, предложение модели, периодическая агрегация `feedback.md` в рекомендации по правке промтов слоёв L1–L5 | `06_feedback_followup.md` |

Дополнительные специализированные промты вне основной цепочки (вызываются по
типу вложения, но по той же схеме «слой = промт + модель»):

| Промт | Когда используется |
|---|---|
| `07_document_clarifying_questions.md` | Загрузка документа (§2.2) |
| `08_photo_people_analysis.md` | Фото с людьми (§4.1) |
| `09_handwriting_transcription.md` | Фото с рукописным текстом (§4.2) |

### 6.1 Почему многослойно, а не один большой промт

1. **Разная стоимость/латентность** — L0/L1/L2 короткие и дешёвые, могут идти
   на дешёвой модели (или локально), L4/L5 требуют более сильной модели с
   доступом к найденному через gbrain контексту.
2. **Проверяемость** — каждый слой можно протестировать и улучшить отдельно
   (промты лежат md-файлами в git — версионируются и ревьюятся как код).
3. **Прозрачность для пользователя** — на L2.5 и в фото/почерке пользователь
   явно подтверждает факты **до** их фиксации — это защита от «домыслов LLM»,
   попадающих в базу как истина.
4. **Явное разделение «извлечение фактов» и «прогноз»** — L2/L3 работают с тем,
   что произошло, L4/L5 — с оценкой, что может произойти. Смешивать их в одном
   промте размывает ответственность за качество.

### 6.2 Где хранится «многослойность» технически

`secondbrain` (новый MCP-компонент, см. §9) держит реестр слоёв
(`secondbrain/src/layers.json` или аналог): для каждого слоя — путь к
md-промту в `Promts/`, модель/провайдер по умолчанию, ожидаемая
JSON-схема ответа. Промты — **обычные md-файлы с frontmatter** (модель,
temperature, схема ответа) + сам текст промта; секретов там нет, поэтому они
свободно коммитятся и ревьюются как документация.

### 6.3 Извлечение фактов vs подтверждение пользователем

Ни один факт (новая персона, привязка решения к персоне, содержание
документа, расшифровка почерка) не попадает в Obsidian-базу **без явного
подтверждения пользователя**, если по нему было неоднозначно. Однозначные
случаи (например, повторно узнанный персонаж с высокой похожестью и без
альтернатив) фиксируются сразу, но всегда с возможностью правки одним
сообщением.

### 6.4 Vision (фото/видеокадры)

Отдельного «слоя с номером» нет — vision используется внутри L0 (кадр →
описание), §4.1/§4.2 (люди/почерк). Технически это вызов
vision-совместимой модели через тот же LLM-провайдер (OpenRouter поддерживает
vision-модели), поэтому отдельного провайдера заводить не нужно — только
явный выбор vision-модели в конфиге (`VISION_MODEL`, по умолчанию модель
основного агента, если она поддерживает vision).

## 7. Хранилище: Obsidian-база

Структура вложенности (том `/opt/data/vault`, монтируется как том amvera,
как и `gbrain`/`grafify`):

```
vault/
├── 00_Inbox/            # сырые, ещё не разложенные записи (временно, до lint)
├── 10_Diary/            # дневниковые записи, по одной заметке на день/сообщение-кластер
├── 10_Photos/           # разборы фото (люди, почерк) со ссылками на attachments
├── 10_Documents/        # заметки о присланных документах
├── 20_People/           # Имя_Фамилия_(роль).md — один файл на персонажа
├── 30_Decisions/        # структурированные решения/сомнения (вывод L3) + прогноз (вывод L5)
├── _attachments/        # оригиналы файлов (фото/документы/аудио) — не в git, только на томе
└── _meta/               # lint-отчёты, журнал обработки
```

### 7.1 Разметка

- Все упоминания людей — только через `[[Имя_Фамилия_(роль)]]` (никогда
  просто текстом, если персонаж уже определён).
- Frontmatter обязателен на всех заметках, кроме `00_Inbox` (черновики):
  ```yaml
  ---
  type: diary | decision | person | photo | document
  date: 2026-07-13
  people: ["[[Иван_Петров_(начальник)]]"]
  source: telegram_channel | telegram_dm | telegram_photo | telegram_voice | telegram_video | upload
  model: anthropic/claude-opus-4.6   # какая модель обрабатывала (для аудита feedback)
  status: draft | confirmed
  ---
  ```
- Файл персонажа (`20_People/Имя_Фамилия_(роль).md`) — обязательные поля
  frontmatter: `role`, `aliases` (варианты написания имени), `first_seen`,
  `handwriting_notes` (если применимо, §4.2).

### 7.2 Линт (`_meta`, промт-независимая проверка)

Перед тем как заметка получает `status: confirmed`, прогоняется детерминированный
линт (без LLM, обычный код в `secondbrain`):

1. Frontmatter валиден и содержит обязательные поля.
2. Все `[[ссылки]]` в теле совпадают с полями `people` во frontmatter и
   существуют как файлы в `20_People/` (нет «битых» ссылок на несуществующего
   персонажа).
3. Нет дублей персонажей (два файла с одинаковым `role`+похожим именем) —
   если найдено, лint не проходит и бот переспрашивает у пользователя, не один
   ли это человек (§3).
4. Дата/имя файла соответствуют конвенции именования.

Результат линта — файл в `_meta/lint/<дата>.md` (что поправлено автоматически,
что требует ответа пользователя) — это тот же принцип, что «lint» в исходном
issue, только формализованный.

## 8. Feedback-wiki

`Promts/_wiki/feedback.md` — append-only журнал (см. §5), плюс агрегированные
`Promts/_wiki/model_stats.md` (какая модель/слой получают больше 👎 — обновляется
слоем L6). Это то самое «wiki-база», о которой просил пользователь — она
физически часть Obsidian-базы (том), но лежит рядом с промтами, потому что
задача L6 — со временем предлагать правки самих промтов на основе этого журнала.

## 9. Технический слой

### 9.1 Компоненты (текущие + новый)

| Компонент | Роль | Статус |
|---|---|---|
| `hermes-agent` | Telegram-шлюз, LLM-оркестрация, `/model`, кнопки/inline keyboard, tool-calling к MCP | уже есть |
| `gbrain` (MCP) | Долговременная память, семантический поиск по фактам/заметкам (эмбеддинги Yandex) | уже есть |
| `Grafify` (MCP) | Граф кода этого репозитория (для разработки, не для данных пользователя) | уже есть |
| Yandex SpeechKit | STT/TTS для голоса | уже есть |
| **`secondbrain` (новый MCP-сервер)** | Инструменты этого ТЗ: Obsidian I/O + lint, реестр персон/дизамбигуация, реестр слоёв/промтов, feedback-журнал + прайсинг моделей, документ/фото пайплайны | **реализуется этим ТЗ** |
| Vision/OCR | Распознавание лиц/поз/почерка — vision-модель через OpenRouter (или отдельный OCR при необходимости) | реализуется этим ТЗ (промты §4, §6.4) |
| Video → audio/frames | Извлечение звука и кадров из видеосообщений | реализуется этим ТЗ (небольшой shell/ffmpeg скрипт, по аналогии с `speechkit/*.sh`) |

`secondbrain` регистрируется в `docker/entrypoint.sh` как ещё один блок
`mcp_servers` (по образцу `gbrain_block`/`grafify_block`), переменные —
по аналогии с существующими (`SECONDBRAIN_ENABLED`, `OBSIDIAN_VAULT_PATH=/opt/data/vault`).

### 9.2 Поток данных (упрощённо)

```
Telegram (канал-дневник ИЛИ чат с ботом)
        │
        ▼
   hermes-agent (шлюз, tool-calling)
        │  MCP tools:
        ├─ secondbrain.ingest(message)         # L0/L1
        ├─ secondbrain.extract_people(text)     # L2   (промт из Promts/)
        ├─ secondbrain.resolve_person(name,ctx) # L2.5 (сверка с gbrain + vault)
        ├─ secondbrain.extract_decision(text)   # L3
        ├─ gbrain.search(query)                 # контекст для L4 (история)
        ├─ secondbrain.forecast(decision, ctx)  # L4 (мульти-перспективный)
        ├─ secondbrain.synthesize(forecasts)    # L5
        ├─ secondbrain.lint(note_path)          # §7.2, без LLM
        ├─ secondbrain.record_feedback(...)     # §5, L6
        └─ secondbrain.model_prices(provider)   # список моделей по цене
        │
        ▼
   vault/ (Obsidian, том amvera) + gbrain (эмбеддинги/поиск)
```

Kнопки 👍👎 — inline keyboard Telegram; hermes-agent уже поддерживает
inline-клавиатуры для встроенных команд (`/model`), поэтому для ответов бота
по каждому решению используется тот же механизм (тул явно просит гейтвей
прикрепить клавиатуру `[["👍","👎"]]` к сообщению, callback обрабатывается
как ответ на инструмент `secondbrain.record_feedback`). Если версия
hermes-agent, зафиксированная в образе, не даёт тулам прикреплять произвольную
inline-клавиатуру к любому сообщению — см. риск в §11 (открытый вопрос №1) и
запасной вариант (эмодзи-реакция вместо кнопок / короткая команда `/fb`).

### 9.3 Приватность и безопасность

- Дневник может содержать очень чувствительные данные (личные решения,
  чужие персональные данные). Доступ — только `TELEGRAM_ALLOWED_USERS` (как
  сейчас); vault и attachments — на приватном томе amvera, не в git.
- В git попадают только: код (`secondbrain/`), промты (`Promts/`), это ТЗ и
  CJM. **Никогда** — содержимое `vault/`, `_attachments/`, `feedback.md`
  реального пользователя (по умолчанию `.gitignore`, см. §9.4).
- Персональные данные третьих лиц (люди из дневника) хранятся только на
  стороне пользователя (его том amvera) — бот не передаёт их куда-либо, кроме
  LLM-провайдера, необходимого для анализа (тот же принцип, что уже действует
  для памяти/эмбеддингов).

| Путь | Назначение |
|---|---|
| `ТЗ.md` | этот документ |

## 10. Нефункциональные требования

- **Русский язык** — весь диалог, промты и служебные тексты по умолчанию на
  русском (как весь остальной репозиторий).
- **Идемпотентность обработки** — если сообщение уже обработано (есть запись в
  `_meta`), повторный запуск `secondbrain` не дублирует заметки.
- **Деградация без падения** — если MCP `secondbrain` недоступен, hermes
  продолжает работать как обычный чат (уже так работает для `gbrain`/`grafify` —
  `enabled:false`/таймаут не роняют шлюз).
- **Стоимость** — L0–L3 по умолчанию используют более дешёвую модель
  (`SECONDBRAIN_FAST_MODEL`), L4/L5 — модель основного агента (`/model`) или
  отдельно заданную (`SECONDBRAIN_ADVISOR_MODEL`).

## 11. Открытые вопросы / риски

1. **Возможности hermes-agent по inline-кнопкам от произвольного тула** —
   требует проверки на реальном образе (см. §9.2). Пока не проверено —
   заложен запасной вариант.
2. **Video-note (кружочки) в Telegram** — распознавание кадров лиц/действий
   для видео может быть дороже по токенам; на первом этапе можно ограничиться
   расшифровкой звука (STT) без анализа кадров, добавить кадры вторым этапом.
3. **Определение «который Иван»** — дизамбигуация на основе одного текстового
   упоминания иногда невозможна без вопроса пользователю; ТЗ сознательно
   выбирает «переспросить», а не «угадать».
4. **BMAD-METHOD vs Spec Kit** — см. §0; решение принято в пользу уже
   установленного Spec Kit, но если владелец репозитория настаивает именно на
   BMAD-METHOD — потребуется отдельное решение (два процесса параллельно не
   заводим).

## 12. Этапы реализации (roadmap)

- **M1 — Фундамент**: `secondbrain` MCP-сервер со скелетом инструментов,
  Obsidian-структура (§7), детерминированный линт (§7.2), реестр
  слоёв/промтов (§6.2). *Без* LLM-вызовов внутри секондбрейна — только

  провайдер основного агента; дизамбигуация персон; создание/обновление
  `20_People/*.md`.
- **M3 — Прогноз**: L4/L5, интеграция с `gbrain.search` за историческим
  контекстом, запись в `30_Decisions/`.
- **M4 — Вложения**: документы (§2.2), фото людей (§4.1), почерк (§4.2), видео
  (§2.1).
- **M5 — Feedback-петля**: кнопки 👍👎, `feedback.md`, сортировка моделей по
  цене, L6-агрегация для ревью промтов.
